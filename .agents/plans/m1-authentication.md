# M1 authentication and authorization implementation plan

Status: approved and implemented. Release HTTPS acceptance and Vite browser verification passed. See the verification record below.

Reuse the [accepted browser and API contract](../../docs/architecture/m0-authentication-design.md), [authentication ADR](../../docs/decisions/0003-stateless-access-and-refresh-rotation.md), [M1 schema](../../docs/architecture/database-schema.md), and [incident rules](../../docs/requirements/incident-intake-and-triage.md).

The starting schema already had users, roles, explicit queue membership, refresh families and credentials, a durable Redis generation record, and distinct append-only audit tables. The seed already hashed private runtime passwords using Argon2id. The API originally exposed infrastructure endpoints. Redis used a PING-only ACL. The API ignored forwarded addresses. The frontend selected synthetic personas and read fixture data scoped by those identities.

## Approved decisions

1. **M1 identity and account scope.** Use the opt-in seed to provision local accounts and expose a read-only profile from the existing safe user summary. Show the current session and sign-out in account settings. Preserve browser-local appearance preferences. A live session and its role labels must never load persona fixtures. Remove the synthetic sign-in entry from the default application when live sign-in ships. A future standalone demo may reuse the fixtures with separate routes, state, and runtime configuration. Keep registration closed. Defer administrator-managed provisioning and identity edits to M2. Review self-service password changes, session enumeration, and revocation of other sessions with live family checks, purpose-bound reauthentication, and account-wide revocation where required. Recovery and email verification require a verified delivery channel and an operator recovery policy. MFA needs enrollment, recovery, and factor reset policies. Keep email, phone, and device identifiers out of the M1 identity schema.
2. **HTTPS proxy trust.** Accept a single normalized source address only from the configured exact socket peer on a dedicated proxy-to-API Compose network, with a configurable reserved proxy address. Nginx overwrites the internal address header from its connection peer. Keep the backend and data services unpublished. The Compose development override reserves the same proxy address for Vite. Its proxy overwrites the internal address header from its own connection peer. Native development trusts a loopback proxy only when explicitly configured. Validate the configured HTTPS origin against incoming browser mutations and ignore generic forwarding headers. Reject authentication admission when source identity cannot be established. The source remains a rate signal. Port forwarding or NAT may legitimately group users into one source bucket.
3. **Cryptography and new dependencies.** Approve PyJWT for access JWTs with a fixed HS256 algorithm and independently generated 256-bit or stronger keys. Only this API signs and verifies access tokens. Use an allowlisted key ID from local configuration. Keep old signing keys available for the maximum access lifetime plus accepted clock skew, unless removed immediately after suspected compromise. Store opaque refresh tokens as keyed digests, with a bounded version in the opaque token and matching configured key. Keep old digest keys until all affected families can expire so previously consumed credentials remain recognizable. Revoke affected families before retiring a compromised digest key early. Use separate keys for CSRF authentication and Redis identity digests, with planned CSRF overlap and limiter generation recovery on limiter-key change. Approve Playwright as a development-only dependency for the actual HTTPS browser suite. Passwords use salted one-way hashes. JWTs carry signed, readable claims. File and backup encryption protects stored data and uses distinct keys. For the current identity fields, use encrypted host storage and encrypted backups as deployment controls. Introducing sensitive fields requires associated encryption, key custody, restoration, and retention decisions. Compose named volumes alone provide persistence.
4. **Browser integration and authorization.** Move live sign-in, profile, and the M1 incident intake and triage routes to server-backed state. Show unavailable features explicitly until their live workflow exists. Use same-origin cookie requests, keep CSRF in memory, and coordinate refresh across tabs with an origin-scoped Web Lock. Recheck the session inside the lock before refreshing and require interactive sign-in when safe coordination or the outcome cannot be established. Route guards and role navigation express UI availability. The API independently enforces current identity, employee ownership, and the explicit L1 role and queue grant. Privileged account changes require their separately approved reauthentication contract.

## Implementation and acceptance

1. **Credentials and ingress.** Add validated secret-file inputs and environment settings, fixed-algorithm JWT validation with required claims, cookie and CSRF helpers, bounded Argon2id verification, and trusted source extraction. Verify both HTTPS entry points, cookie attributes and deletion, host/origin validation, header handling, and safe errors and logs.
2. **Limiter and sessions.** Use narrow Redis command and key grants. Check the generation marker with atomic counter updates and expiry. Apply aggregate admission before cardinality can grow, then source and identity checks at the accepted stages. Persist recovery coordination in PostgreSQL across Redis and backend restarts. Verify bounded admission at concurrency and fail-closed login and refresh during loss, reset, and cooldown. Use a single lock order for family operations, re-read state under the lock, and commit rotation or revocation and audit before responding. Verify strict reuse, current-credential logout with expired access, idempotence, concurrent refresh and logout, rollback, and audit privileges. Ordinary access keeps the accepted residual JWT window. Logout keeps its PostgreSQL-only path. Redis remains a limiter, with no permissions or durable session state cached.
3. **Authorize the incident slice.** Use current roles and queue grants on every relevant request. Scope lookups in PostgreSQL, return the same result for missing and out-of-scope tickets, and write incidents and triage with their audit records atomically. Verify that administrator status alone grants no incident visibility. Guard triage by the accepted state transition and ticket revision.
4. **Integrate and verify the browser.** Verify login, reload/bootstrap, current profile, localized errors, protected navigation, cross-tab refresh, logout, employee intake and tracking, and L1 triage through the local HTTPS front door with isolated real PostgreSQL and Redis. Verify rejects and absence of credential or personal data leaks in responses, storage, and logs. Record actual commands and evidence in the API and database documentation, threat model, security standards, config examples, README, roadmap, and project state. Keep attachment API work in its approved follow-on.
