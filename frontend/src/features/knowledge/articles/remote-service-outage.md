## Confirm what is affected

Check whether coworkers who use the same service see the same failure. Compare results from another floor, location, or network only if you can do so safely. A short comparison helps support distinguish a shared outage from an individual connection problem.

### Summarize the evidence

| Detail | Example | Why it matters |
| :--- | :--- | :--- |
| Service | An internal scheduling application | Routes the issue to the right team |
| Scope | Several people on one floor | Helps establish the likely boundary |
| Start time | Around 09:20 local time | Helps compare related events |
| Work impact | The morning schedule cannot be updated | Informs triage |

## Report the issue once

1. Open an incident with a short, specific summary.
2. Provide the exact error, when it started, and how many people are known to be affected.
3. Mention available workarounds and identify any work blocked.
4. Record new evidence in replies to the same ticket.

### Keep the priority information clear

Use Request prompt review when the impact warrants attention. L1 assesses priority from impact and urgency during triage. Include supporting details so the agent can make that assessment.

#### Examples of useful impact details

- Staff can view the schedule but cannot save changes.
- Another office can still access the service.
- The team is using a manual workaround until the service recovers.
