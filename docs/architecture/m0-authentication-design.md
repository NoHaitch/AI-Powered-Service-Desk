# M0 design — authentication and incident intake

**Status:** Accepted M0 baseline. The first-slice contracts, threat model, and evaluation plan apply in M1 after separate scaffolding authorization. See the [incident requirements](../requirements/incident-intake-and-triage.md) and [authentication decision](../decisions/0003-stateless-access-and-refresh-rotation.md).

## Selected design and alternatives

Use a short-lived signed JWT access token and a rotating, high-entropy **opaque** refresh token in separate HttpOnly cookies. FastAPI verifies access JWTs locally with trusted signing keys and claim validation. Ordinary verification performs no PostgreSQL or Redis lookup for the credential or token family. PostgreSQL owns account, role, token-family, and durable revocation state. Use same-origin HTTPS with Vite proxying in development and Nginx preferred for local releases.

| Option | Benefit | Cost or limitation |
| --- | --- | --- |
| JWT access, opaque refresh | A standard signed access credential can later be verified at a trusted boundary. An opaque refresh token contains no claims and can be looked up by digest. | Requires transactional refresh state and signing-key management. Immediate revocation and fresh RBAC still require authoritative checks. |
| JWT access and JWT refresh | A signed refresh token can carry a grant identifier and expiry. | Rotation, logout, and reuse detection still require server-side state. Adds claim validation, key management, and token-type confusion risk for little benefit here. |
| Opaque server-side session | One browser credential and straightforward revocation. Fits the local monolith. | Each request requires a lookup. A later gateway integration would need a trusted identity boundary or token exchange. |

Credential verification and resource authorization are separate. Protected incident queries still enforce requester ownership and current queue or role grants as part of the resource operation. Use the JWT subject from verified claims. Where a current role, account status, or scope is necessary, obtain it from authoritative application data and deny if unavailable. A route that relies solely on valid claims can accept a revoked access token until expiry. Logout, detected refresh reuse, and account-wide revocation stop further refresh issuance immediately after the PostgreSQL transaction commits. They do not invalidate already issued access JWTs on the default stateless path.

The [M1 operations guide](m1-authentication.md) describes the implemented ingress, key management, account provisioning, and verification workflow.

## Browser and credential policy

- Use one trusted HTTPS origin in development and local release. Set credential cookies `HttpOnly`, `Secure`, and `SameSite=Lax`, with no `Domain`. Scope the access cookie to the API and the refresh cookie to the auth route group so it reaches both refresh and logout. `Path` limits where cookies are sent and is not an authorization boundary. Match cookie name and path on deletion. Verify cookie behavior in the actual browser.
- Require exact trusted `Origin` on browser mutations, including login, refresh, and logout. Require `X-Desk-Request: 1` and JSON for login. After login, require a signed CSRF token in a custom header for mutations. Bind it to the family ID from the verified access JWT, or to the family resolved during a refresh or logout. Ordinary access requests therefore need no CSRF-state lookup. Return the separate token at login or from the bootstrap endpoint after a reload. Keep it in frontend memory. Reject missing or invalid tokens and untrusted origins. Keep reads free of business side effects and disable credentialed cross-origin access by default.
- Use Argon2id through an established library. Store salted hashes, calibrate parameters on the target local container, and bound authentication request volume and concurrent hashing. Use generic login errors for invalid or disabled accounts and keep passwords out of logs and seed files.
- For access JWTs, allow only the configured signing algorithm. Validate signature, issuer, audience, expiry, token type, subject, and family identifier. Include only necessary claims. Resolve the user's current roles and permitted queue scope server-side. Keep signing material outside version control and define rotation before release.
- Accepted initial defaults are **10 minutes** for access, **24 hours** for refresh inactivity, and **7 days** absolute from login. Rotation extends the inactivity deadline only within the absolute cap. Bound access expiry and cookie lifetimes by server-side deadlines. Refresh inactivity measures time since the last successful refresh. Avoid unattended background refreshes that would defeat the inactivity limit.

## Replay protection trade-offs

The first slice combines stateless short-lived access credentials, strict single-use refresh rotation, and family revocation on detected reuse. An access JWT remains replayable within its validity window unless a route performs an additional revocation or authorization check. Rotation detects reuse of a consumed refresh credential. It cannot identify which presenter is legitimate. The [project security standards](../../.agents/rules/SECURITY_STANDARDS.md) apply regardless of token format.

| Mechanism | Effect | Disposition |
| --- | --- | --- |
| JWT ID (`jti`) | A unique ID can support correlation or a per-token denylist. The ID alone does not stop reuse. Marking normal access tokens single-use would break valid repeated and parallel API calls. | Use only if correlation or targeted revocation is needed. The first slice revokes refresh families. |
| Rotating refresh tokens | Detects reuse through persisted lineage. A race or lost response can resemble theft and require reauthentication. | Use atomic rotation and strict family revocation. Verify browser coordination and recovery in M1. |
| Sender-constrained tokens | Proof-of-possession mechanisms such as DPoP or mutual TLS bind a credential to a key and establish an additional check at the receiver. Browser key handling, proof validation, and gateway integration add work. | Defer until a service or external-client threat justifies the complexity. |
| IP or device context | IP changes, shared addresses, and device signals can be noisy or spoofable. Collection has privacy and retention costs. | Consider minimal risk signals for auditing or step-up verification only with evidence. Keep strict IP and device binding out of the first slice. |

## Sensitive operations and Redis

Routine incident submission, reads, and L1 triage use stateless JWT verification, current resource authorization, and CSRF for mutations. Check the active family and current permissions in PostgreSQL on sensitive routes such as credential and privilege changes, revoking other users' sessions, or sensitive exports. Recheck within the mutation boundary so permission or family changes cannot race a privileged write. Credential and privilege changes also require single-use reauthentication proof bound to the user, family, and intended operation and target, valid for **5 minutes** and consumed with the mutation. Audit issuance, use, and denial. Refresh never renews proof. If fresh proof or live state is unavailable, deny the sensitive action. No credential or privilege management endpoint is needed for the M1 seeded-account slice.

Introduce private **Redis in M1 for authentication rate limiting**. Login and refresh return a safe `503` when required counters cannot be checked or written or state integrity is uncertain. Logout remains available through PostgreSQL. Other routes continue if their own checks and data sources are available. Optional data caches may fall back to authorized PostgreSQL reads.

Defer a Redis denylist until a use case needs faster access-token invalidation. It can only affect routes that consult it. PostgreSQL must commit revocation and audit state first. An optional later projection should use durable publication, retry and reconciliation, and entries retained through the last affected token expiry. Prevent eviction or data loss from silently removing security state. A missing key cannot prove validity if projection freshness, completeness, or restart recovery is uncertain. Routes promising immediate revocation should consult PostgreSQL or deny when they cannot establish fresh state. An asynchronous Redis projection alone cannot guarantee immediate revocation.

## Configurable limiter defaults

| Control | Accepted initial default | Enforcement |
| --- | --- | --- |
| Aggregate admission | 120 login or reauthentication attempts per minute, and 300 refresh attempts per minute in a separate bucket | Apply before allocating per-identifier keys or expensive work. Keep a separate bounded worker budget for password hashing. |
| Login by source | 60 attempts per 5 minutes | Admit before account lookup or hashing. Also bound request size and aggregate hashing concurrency. |
| Login by identifier and source | 5 attempts per 5 minutes | Apply to any normalized identifier, whether known or unknown. Do not lock the whole account. |
| Login account-wide signal | 15 failed attempts per 15 minutes across sources | Alert signal only. Avoid a remotely triggerable permanent or account-wide hard lock. Revisit step-up or adaptive throttling if distributed guessing becomes material. |
| Refresh by source | 30 attempts per minute | Admit before PostgreSQL lookup. Keep this budget separate from login. |
| Refresh by verified family | 6 rotations per minute | Apply after credential and CSRF checks. Detect recognized reuse before applying the family rotation limit so the limit cannot suppress revocation for admitted requests. |
| Reauthentication when introduced | 5 attempts per family per 5 minutes and the login source budget | Apply before password hashing. Use the same outage safeguards for credential verification. A successful proof expires after 5 minutes or on use. |

Treat these as positive, bounded settings with explicit units. Reject invalid release configuration at startup. Use a shared bounded fixed-window limiter for M1. At the first counted attempt, set a TTL equal to the window. Update counts and expiry atomically so concurrent requests cannot bypass limits or leave permanent counters. Rejected attempts must not extend the window. Fixed windows allow bursts at the boundary, so tune limits and password-hashing concurrency against the local capacity test. Inspect shared-IP behavior before considering a stricter source limit.

Derive source identity from the peer or trusted proxy chain and normalize it consistently. Do not trust client-supplied forwarded addresses. Use keyed digests for normalized identifiers, source addresses, and family counter keys. Bound key cardinality with an aggregate admission budget before creating per-identifier keys. Return generic credential failures and comparable verification work for unknown, disabled, and wrong-password accounts within the same admission limits. Return generic throttling responses without identifying the exhausted bucket. Source address is a rate signal only.

Use a bounded non-evicting Redis limiter allocation. A write failure is unavailability, and a missing key is normal only while the limiter generation is known healthy. For M1, treat an unexpected Redis restart, missing state marker, or suspected reset as unavailable. Use a configurable recovery cooldown at least as long as the longest enforced counter window, **5 minutes with these defaults**. Measure from detection when the last safe time is unknown. Track the recovery deadline or generation outside the reset-prone counters so a backend restart cannot skip it. An explicitly initialized empty deployment may start normally. Resume only after the health write and recovery checks pass. Preserving counters across ordinary restarts could reduce downtime later, provided lost or stale state is detected.

## API contract

The browser never receives the access or refresh token in JSON. Auth and CSRF responses use `Cache-Control: no-store`. Auth cookies are for browser API requests. Future gateways or services use separately designed audience-scoped credentials and trust boundaries.

| Operation | Success behavior | Boundary |
| --- | --- | --- |
| `POST /api/v1/auth/login` | `200`, set both cookies and return a safe user summary and CSRF token. | Validate origin and request shape, rate-limit attempts, verify Argon2id hash, and create one refresh family. |
| `GET /api/v1/auth/csrf` | `200`, return a family-bound CSRF token for a valid access or current refresh credential. | No token rotation or deadline extension. No credentialed cross-origin reads. |
| `GET /api/v1/auth/me` | `200`, return current user and role information for the UI. | Verify access JWT statelessly and read current user data. Ordinary authentication does not look up family status. UI roles are advisory. |
| `POST /api/v1/auth/refresh` | `204`, replace both cookies after rotation commits. | Require origin and CSRF checks. Authenticate the presented refresh credential and enforce family limits. |
| `POST /api/v1/auth/logout` | `204`, revoke the current refresh family and clear auth cookies. Previously issued JWTs can retain validity on stateless routes until expiry. | Require origin and CSRF for a recognizable family. Support logout with expired access using the current refresh credential. Idempotent for an already revoked family. A failed database write returns a safe error and does not report revocation success. Redis is unnecessary. |
| `POST /api/v1/incidents`, `GET /api/v1/incidents` | `201` with the created incident reference, or `200` with the employee's own incidents. | Authenticated employee. Require CSRF for create. Validate fields and write the incident and audit event atomically. |
| `GET /api/v1/incidents/{id}` | Return ticket fields allowed for the requester or an authorized L1 queue member. | Scope lookup by identity and queue grants. Return `404` for missing or out-of-scope incidents so IDs cannot reveal existence. |
| `GET /api/v1/queues/l1/incidents`, `POST /api/v1/incidents/{id}/triage` | `200` with authorized intake entries, or `200` with the updated incident after assessment, derived priority, transition, and audit event commit. | Require L1 role and queue scope. Validate CSRF for triage and guard the `New → Triaged` update against races. |

Login accepts `username` and `password`. The safe user summary exposes the user ID, display name, and roles. Incident creation accepts `summary`, `description`, and optional boolean `prompt_review` (default false). Triage accepts `impact` and `urgency` as `low`, `medium`, or `high`. Reject unexpected server-owned fields. Incident views expose the reference, summary, status, priority (null before triage), and timestamps as allowed for the caller. Detail views include the description. Staff views add only the queue and assessment details that their role permits. The L1 intake queue lists `New` entries, oldest first with a stable ID tie-break, and supports the `flagged_only` filter. Both incident lists accept `offset` and a bounded `limit` up to 100. Raw audit records require separate staff authorization.

Return `401` for absent or invalid credentials, `403` for CSRF or a denied role, `404` for out-of-scope resources, `409` for stale or invalid transitions, and `422` for invalid input. Return `429` for an enforced limit with a coarse `Retry-After` and `503` for limiter outage or recovery, before issuing tokens. The client honors backoff and does not loop or clear a usable session solely because login or refresh is temporarily unavailable. An unavailable authoritative store fails closed. The UI may coordinate a refresh after access expiry and must avoid blindly repeating mutations with unknown outcomes.

### Attachment API extension under review

Preserve JSON incident creation without attachments. A future optional list of staged attachment IDs can be claimed atomically when creating an incident. Existing-ticket uploads will use the same staged-object primitives and require a separately authorized parent mutation. Listing and download must check current access to the ticket and use the out-of-scope `404` rule. All attachment mutations require validated Origin and CSRF. Responses never expose filesystem paths, object keys or private digests. Download uses an explicit attachment disposition, safe filename, no-sniff, and private no-store. No attachment routes are registered yet.

For the threat model, consider unauthorized object claims and cross-ticket disclosure, parser attacks and content spoofing, traversal, malformed filenames, disk exhaustion, interrupted writes, and tampered restored files. Keep uploads bounded, verify decoded content and file integrity, and audit lifecycle state changes. API-level denial, CSRF, and HTTP response tests are due when those routes ship. [Attachment controls and limits](content-storage.md#attachment-foundation)

## PostgreSQL data contract

Apply the [database standards](../../.agents/rules/DATABASE_STANDARDS.md) and the accepted [session and migration design](postgresql-integration.md). Ordinary stateless JWT verification remains outside the database session path. The [implemented schema](database-schema.md) represents each M1 incident as a ticket UUID and a required incident detail row. A separate immutable human-readable reference complements the UUID. The initial schema follows these invariants:

- Use UUID entity identifiers and UTC-aware PostgreSQL timestamps. Give each normalized login identifier a unique constraint. Model role and queue memberships with foreign keys and composite uniqueness.
- Give refresh digests unique constraints. Enforce at most one unconsumed credential per family with a partial unique index. Expired but unconsumed credentials still occupy that slot. The rotation transaction checks expiry and family status. Constrain predecessor/successor relationships to the same family and prevent multiple successors for one predecessor.
- Keep incident ownership and queue references non-null. Allow null impact, urgency, and priority before triage. For a triaged incident require all three, with explicit non-null and valid-range checks. A conditional update guards the expected state or revision. The database enforces valid stored values while the domain layer owns the priority matrix.
- Restrict deletion of records needed for retained history or security audits. Use append-only audit privileges at runtime. Keep policy-governed auth audit expiry separate from application writes and from deferred hard deletion or anonymization workflows.

| Record | Required state and invariants |
| --- | --- |
| User and role grants | Stable user ID, unique normalized local username, separate display name, password hash, account status, and role/queue grants. Store the canonical username and enforce its shape and uniqueness in PostgreSQL. The authenticated actor comes from server-validated credentials. |
| Token family | Family ID, user reference, authentication and last-refresh times, idle and absolute deadlines, and revocation time/reason. One family represents one login. Use UTC timestamps. Read at refresh, logout, and explicitly sensitive operations. |
| Refresh credential | Unique digest of the opaque credential, family reference, issuance and expiry, consumption time, and predecessor/successor relationship. Keep consumed digests for the reuse-detection window, at least while the family could still be active. Keep raw tokens out of persistence. |
| Limiter state | Expiring counters in Redis keyed by operation and privacy-preserving bucket identity. Store no raw credentials. Keep active recovery generation and deadline outside the disposable counters. |
| Reauthentication proof (future) | User and family binding, intended operation and target, verified-at and expiry timestamps, and single-use consumption state. Keep it separate from ordinary token refresh state. |
| Incident | Stable ID, requester reference, summary, description, status, L1 queue/tier, nullable impact/urgency/priority until triage, timestamps, concurrency guard, and non-null prompt-review flag defaulting to false. Enforce the approved field limits on stored values. |
| Audit event | Event ID, time, actor when known, action, outcome, affected resource or family reference, and request correlation ID. Audit login success, a bounded sample of credential denials, rotation, reuse, logout, and administrative revocation when introduced. Request telemetry counts refusals without credential or identity details. Restrict staff access and define retention. Exclude raw cookies, tokens, passwords, and sensitive payloads from both ingress and application logs. |

Serialize refresh rotation at the token-family level. Reserve aggregate and source admission first. Check the short, bounded Redis family counter under the family lock after testing for reuse. Fence token issuance against the durable limiter generation in the same PostgreSQL transaction. Revalidate the credential and family under the transaction lock before any mutation. In one transaction, consume the old credential before inserting its successor, advance the idle deadline, and record the outcome. A recognized consumed credential presented with valid request protections revokes the whole family and records reuse, including when its family rotation budget is exhausted. Unknown credentials must not affect unrelated families. Commit revocation before returning the failure response. Handle logout under the same serialization boundary.

Use strict single-use rotation with no retry grace window. Coordinate refresh across tabs and retry waiting resource requests only after a known successful refresh. Use the PostgreSQL family lock to serialize logout and refresh. If logout commits first, refresh fails. If refresh commits first, logout revokes its successor too. Stop new refreshes when logout begins and coordinate in-flight requests so logout clears cookies last where possible. Ignore stale UI results after logout. The browser may still apply a late `Set-Cookie`, so test out-of-order responses and the residual access window. A legitimate duplicate or lost response can still require reauthentication. Avoid automatically retrying an ambiguous refresh.

## Authentication and Redis observability

Follow the [observability architecture](observability.md). Use correlation IDs and structured logs for operation, outcome, reason class, and duration. Measure login and refresh responses, throttles, limiter latency/errors, outage and recovery transitions, and refresh reuse as bounded signals. Group by operation and outcome. Omit credentials, IP addresses, account identifiers, family identifiers, CSRF values, and raw Redis keys from operational telemetry. Store security-sensitive outcomes, including reuse, revocation, reauthentication, and limiter state changes, in protected PostgreSQL audit records. Aggregate high-volume denials to protect storage; keep state-changing security decisions individually auditable.

API liveness stays independent of Redis. Report auth limiter readiness separately with a bounded check of actual limiter availability, using internal or minimal health details. Report degraded auth without marking unrelated routes unavailable. Failed metrics exporters or collectors must never authorize an operation or suppress required audit writes.

## Threat model and evaluation

Trust boundaries are browser to HTTPS ingress, ingress to FastAPI, and FastAPI to PostgreSQL, Redis, and operational logs. Vite assets and browser input are untrusted. The edge proxy replaces the dedicated source header, and only its exact socket peer is trusted. The single-host private bridges are a distinct transport boundary from browser TLS. Keep refresh credentials, signing keys, password hashes, role grants, and audit records within their intended boundaries.

Apply STRIDE across these boundaries. Spoofing covers stolen credentials, tampering covers JWTs and ticket mutations, repudiation covers missing audit evidence, information disclosure covers cross-user data and logs, denial of service covers login load and dependency outages, and elevation of privilege covers role and queue bypasses. Use applicable ASVS controls and CWE identifiers to trace tests where they clarify the evidence.

| Risk | Control | Planned evidence |
| --- | --- | --- |
| Credential guessing, theft, and fixation | Argon2id, generic errors, rate limits, new family on login, and no secret logging. | Seed synthetic users. Verify invalid and disabled users receive generic failures, compare container hashing cost, and confirm no credentials appear in logs. |
| CSRF, browser-origin confusion, and XSS | Origin checks and session-bound CSRF for writes, secure cookie attributes, output encoding, and no browser token storage. HttpOnly limits token reads but scripts executing in origin can still act as the user. | Browser checks for login CSRF and cross-origin create, refresh, and logout. Verify cookie paths and attributes, rejection of missing or wrong-family CSRF, safe rendering of incident input, and denial from untrusted origins. |
| Forged forwarding headers | Overwrite the dedicated source header at ingress. Require the single configured proxy socket peer. | Confirm header variants share one rate bucket and direct admission over an untrusted socket fails. |
| JWT forgery or stale authorization | Verify JWT claims locally. Enforce current resource permissions. Require live family checks only on routes that explicitly need them. | Assert ordinary credential verification performs no PostgreSQL or Redis reads. Test tampering and bad claims, deny revoked families on sensitive routes, and verify claim-only routes accept a valid outstanding JWT only through its bounded expiry. Test cross-user and cross-queue denial and role removal where fresh data is required. |
| Refresh replay or races | Transactional rotation, family revocation, bounded lifetimes, and frontend refresh coordination. | Use real local PostgreSQL with concurrent refresh and logout requests. Test a consumed-token replay, lost response, unrelated family isolation, and idle/absolute expiry with a controlled clock. Verify at most one successor and durable revocation. |
| Partial ticket or audit writes | Domain rules and revision guards inside a transaction. | Verify one successful triage under competing updates, no partial event after a failed write, and appropriate redaction and staff-only audit visibility. |
| Unsafe ticket input or overposting | Validate payload shape and limits, derive owner and privilege-bearing fields server-side, use parameterized queries, and encode rendered content. | Test unexpected fields, oversized requests, inert injection-like text, and attempts to supply another requester or change priority outside authorized triage. |
| Unavailable authorization state or dependency | Fail closed for protected operations. Use bounded timeouts and keep optional caches and future inference outside the authorization path. Return a stable error response with a correlation ID and protect diagnostics. | Interrupt PostgreSQL during authorization and state changes. Verify denial or a safe service-unavailable response, no sensitive error details, and no partial incident, refresh, or audit write. |
| Redis failure or limiter state loss | Fail closed for rate-limited token issuance. Preserve PostgreSQL logout and ordinary stateless checks. Keep optional caches outside authorization and account for Redis restart and eviction. | Exercise Redis timeout, memory errors, and restart; verify `503` on login and refresh when rate-limit state is unavailable, normal logout with PostgreSQL available, and no accidental bypass. If a denylist is introduced, simulate missed updates, lag, and key loss and verify the authoritative fallback. |
| Enumeration, shared-IP blocking, and resource exhaustion | Apply identifier/source limits independent of account existence. Keep account-wide thresholds advisory. Bound hashing and key creation. | Compare known and unknown responses and timing, test shared-IP and distributed attempts, burst at a window boundary, and verify concurrent increments, expiries, and no TTL extension on denial. |
| Sensitive action with stale proof, when account management is introduced | Check the current family, permissions, and recent operation-bound proof at mutation time. | Test revoked, expired, replayed, wrong-target, and concurrently consumed proof before enabling sensitive actions. |
| Telemetry leaks or outage | Redact identifiers and secrets, keep label cardinality bounded and security audits durable. | Inspect normal and failure logs and metric labels. Verify auth readiness transitions, counter-loss cooldown surviving backend restart, and unaffected routes and audit persistence with collection disabled. |
| Identity collision or loss of retained history | Normalize usernames consistently, enforce PostgreSQL uniqueness, and restrict deletion independently of audit expiry. | Verify mixed-case and padded aliases share one identity and rate-limit bucket. Reject invalid usernames and verify passwords with significant whitespace. Exercise the 90-day auth retention boundary with a controlled clock, preserve incident history and live refresh lineage, and reject unauthorized deletion. |
| Revocation scoped incorrectly | Revoke the affected family for logout or reuse and all families for the accepted account-wide triggers. | Use multiple families across two accounts to prove scope and audit atomicity. Test account-wide effects as each trigger is introduced. Verify ordinary JWT expiry and immediate denial on live-check routes. |

Run domain and security unit tests, API contract tests, PostgreSQL integration tests, and a browser flow covering login, incident intake, L1 triage, refresh, and logout in local Compose. Keep ordinary checks independent of hosted services. Record actual results at the local merge gate. Longer-term capacity testing should include authentication workload limits without using live credentials.

## Login and record lifecycle policy

1. **Login normalization.** Use a local username for M1. Trim surrounding whitespace, accept 3–64 ASCII letters, digits, dots, underscores, or hyphens, and lowercase it before lookup, persistence, and limit bucketing. Enforce uniqueness on the normalized value. Keep display names separate. Preserve passwords exactly as submitted, including surrounding whitespace, and reject unsupported lengths explicitly.
2. **Audit and deletion.** Retain authentication and security audit events for 90 days by default, configurable by deployment. Keep incident business history for as long as its incident is retained. Disable users and restrict deletion of users or incidents with retained history. M1 exposes no hard-delete endpoint. Any record hard deletion or anonymization requires a separately reviewed workflow. Keep auth audit expiry separate from incident history and refresh-token lineage retention.
3. **Account-wide revocation.** Revoke all refresh families on password change or reset, account disablement, role or privilege change, or an explicit revoke-all action. Reuse and ordinary logout revoke only the affected family. The account-wide alert alone never revokes credentials. Current authorization checks deny stale permissions where required, and the accepted residual access-JWT window still applies to claims-only routes.
4. **Incident policy.** Apply the approved field limits, priority matrix, and queue behavior in the [incident requirements](../requirements/incident-intake-and-triage.md).

M1 owns dependency pins, local certificates, proxy configuration, schema migrations, exact pagination parameters and payload field names beyond this contract, and measured pool, timeout, and password-hashing budgets. Optional observability collection is outside the M0 and M1 gates.
